# Pattern bindings for `while`, `for`, and `do` statements

Status: approved design, ready for an implementation plan.

## Context

PR #3976 adds support for type patterns in `instanceof` expressions, starting with
`if` statements:

```java
if (obj instanceof String s) {
    s.length();
}
```

The `if` implementation establishes the pieces this design builds on:

- `InstanceofPattern` in the Java AST.
- `BindingVariableVisitor`, which computes the pattern variables that are definitely
  matched when a guard evaluates to `true` / `false`.
- `#posBinding` / `#negBinding`, which expand to the corresponding declarations.
- `isBindingExpr` and `alwaysAbnormallyTerminates` variable conditions.
- `ifUnfoldPattern` / `ifElseUnfoldPattern`, which declare pattern variables in the
  branches where they are definitely matched.

Loops need the same treatment, but they differ from `if` in three important ways:

1. The guard is evaluated once per iteration, so a binding declaration must be
   re-established on every iteration.
2. The guard's false branch is the loop exit, so `whenFalse` variables are introduced
   *after* the loop, not in an `else` branch.
3. A reachable `break` targeting the loop suppresses the after-loop variables
   (JLS 6.3.2.3–6.3.2.5).

## Goals

- Support type patterns in `while`, `for`, and `do` guards with the same JLS flow
  scoping as `if`.
- Expose pattern variables to JML assertions inside loop bodies and after loops.
- Keep the loop treatments unchanged: loop-scope invariant, loop-scope expand, loop
  invariant, and loop expand must all work on the rewritten loop.
- Preserve loop invariants, free invariants, variants, and loop contracts.
- Keep rule selection deterministic and the taclet oracle stable.

## Non-goals

- General pattern matching beyond `instanceof` type patterns (record patterns,
  switch patterns).
- A complete rework of expression-level pattern evaluation; the existing
  `instanceof` assignment rules remain the basis.
- Pattern variables inside loop invariants. The invariant is evaluated outside the
  body, before the guard has matched, so the variable is not in scope there.

## JLS semantics

JLS 6.3.2.3–6.3.2.5 defines the flow scoping:

| Statement | Definitely matched when the guard is true | Introduced after the statement |
|---|---|---|
| `while (e) S` | `S` | `whenFalse(e)`, if `S` has no reachable `break` for which the `while` is the target |
| `for (init; e; upd) S` | `upd` and `S` | `whenFalse(e)`, if `S` has no reachable `break` for which the `for` is the target |
| `do S while (e)` | none; `S` runs before the guard | `whenFalse(e)`, if `S` has no reachable `break` for which the `do` is the target |

Consequences:

- `while (o instanceof String s)` binds `s` in the body, but not after the loop.
- `while (!(o instanceof String s))` binds `s` after the loop (if no break).
- `do { ... } while (!(o instanceof String s))` binds `s` after the loop, but not in
  the body.
- A `break` that targets the loop means the loop may exit without the guard being
  false, so the after-loop variables are not introduced.

## Core idea: rewrite the loop once, before loop treatment

The obvious standalone after-loop rule would re-fire after `loopUnwind`, because the
recursive `while` is the same loop object with the same binding guard. The rewrite
below avoids that by making the rewritten loop guard a plain boolean.

For `while (e) S`:

```java
boolean b = e;
while (b) {
    #posBinding(e);          // declarations for whenTrue(e)
    S';                      // S with target continues replaced
    b = e;                   // re-evaluate the guard
}
#afterLoopBinding(e, S);     // declarations for whenFalse(e), maybe empty
```

Properties:

- `e` is evaluated once before the first iteration and once at the end of every
  normal iteration, exactly matching `while` semantics.
- A `continue` at loop depth 0 is replaced by `{ b = e; continue; }`, so the guard is
  never frozen.
- A `break` exits before `b = e`; the after-loop declarations are omitted when a
  reachable unlabeled `break` targets the loop.
- The rewritten guard is `b`, so `isBindingExpr(b)` is false. The rewrite rule cannot
  fire on the recursive `while` generated by unwinding. No marker flag is needed.
- The body's `#posBinding` makes the pattern variables available for the whole body,
  including the update part of a `for` loop.
- The after-loop declarations are spliced into the **enclosing block**, so they are
  visible to the statements after the loop.

### `for`

A `for` cannot simply be normalized first: `for_to_while` wraps the result in a block
to scope the init variables, and after-loop declarations placed inside that block
would not be visible after the original `for`. The rewrite therefore handles the
`for` directly:

```java
{ init
  boolean b = e;
  while (b) {
      #posBinding(e);
      S';                  // target continues -> { upd; b = e; continue; }
      upd;
      b = e;
  }
}
#afterLoopBinding(e, S);
```

- The surrounding block gives the init variables exactly the original `for` scope.
- The after-loop declarations are outside that block, in the enclosing block.
- A `continue` executes the updates and refreshes `b` before continuing.
- The generated `while` is the loop to which the loop specification is copied.

### `do`

A `do` body runs before the guard and must not see the pattern variable. The existing
`doWhileUnwind` normalization already handles the first iteration, labeled breaks and
continues. The rewrite:

1. Normalizes the `do` with the same `WhileLoopTransformation` logic as
   `doWhileUnwind`, producing `{ firstBody; while (e) body }`.
2. Rewrites that generated `while` with the `while` rewrite above.
3. Places the after-loop declarations **outside** the normalized block.

The first body stays unbound; only the generated `while` body gets `#posBinding`, and
it only runs after the guard matched.

## Rule and transformer

### Taclet

Add two rules to the Java rule file: one for the program block itself and one for
nested blocks.

```text
patternLoopUnfold {
  \find(\modality{#allmodal}{ #slist }\endmodality (post))
  \varcond(\isBindingExpr(#slist))
  \replacewith(\modality{#allmodal}{ #rewritePatternBlock(#slist) }\endmodality (post))
  \heuristics(pattern_loop_binding)
  \displayname "patternLoopUnfold"
}

patternLoopUnfoldNested {
  \find(\modality{#allmodal}{.. { #slist } ...}\endmodality (post))
  \varcond(\isBindingExpr(#slist))
  \replacewith(
    \modality{#allmodal}{.. { #rewritePatternBlock(#slist) } ...}\endmodality (post))
  \heuristics(pattern_loop_binding)
  \displayname "patternLoopUnfoldNested"
}
```

- `#slist` is the direct statement list of a `StatementBlock`. The root rule matches
  the program block; the nested rule matches a block statement inside the program.
  Together they cover loops in the top-level block and loops inside nested blocks.
- `\isBindingExpr(#slist)` reuses the existing condition. It is extended to accept a
  loop statement (by inspecting its guard), a `Guard`, and a statement list (true if
  any direct statement is a loop whose guard binds).
- Because the rule operates on the actual block list, the loop object is the actual
  AST node; loop-specification and loop-contract copying is reliable.
- Labeled loops and unbraced loop bodies are not direct `LoopStatement`s of the list,
  so they are excluded conservatively.
- The fresh boolean and the labels for the `do` normalization are created by the
  transformer, not by `\new`/`\newLabel` taclet conditions. A transformer does not
  see those fresh instantiations in `SVInstantiations`, so creating them in the
  transformer is the reliable path.

### Condition

Extend `BindingExpressionCond` (registered as `isBindingExpr`) with three additional
accepted shapes:

- a `LoopStatement` (`while`, `for`, `do`): use its guard expression;
- a `Guard`: use the wrapped expression;
- an `ImmutableArray<Statement>`: true if any direct statement is a loop whose guard
  satisfies `BindingVariableVisitor.binds`.

The existing expression behaviour is unchanged, and `toString()` stays
`\isBindingExpr(<sv>)`, so the taclet oracle remains stable.

### Transformer

Add `PatternLoopRewriter` (meta-construct `#rewritePatternBlock`) with the single
argument `#slist`:

1. Read the statement list from the schema instantiation.
2. Scan it for the first `LoopStatement` whose guard satisfies
   `BindingVariableVisitor.binds`. Statements before it are copied unchanged.
3. Create the fresh boolean guard with `TermBuilder.newName("b")` and register it in
   the program-variable namespace.
4. Branch on the loop kind:
   - `While`: build the rewrite directly.
   - `For`: emit the for-init declarations as local-variable declaration statements,
     build the init-scoped block, the `while`, and the outer after-loop
     declarations.
   - `Do`: invoke the existing `WhileLoopTransformation` normalization with fresh
     labels created by the transformer, rewrite the generated `while`, and hoist the
     after-loop declarations outside the normalized block.
5. Compute `whenTrue` / `whenFalse` with `BindingVariableVisitor.analyze(guard)`.
6. Rewrite target `continue` statements:
   - only continues at loop depth 0 with no label;
   - replace with `{ <updates if any>; boolv = guard; continue; }`;
   - leave continues of nested loops and labeled continues to outer loops alone;
   - preserve the original `PositionInfo` on the generated continue.
7. Build the new `while`:
   - body = `whenTrue` declarations, rewritten body, `boolv = strippedGuard`;
   - `strippedGuard` replaces every `InstanceofPattern` by a plain `Instanceof`; it
     is used for the body-end refresh and the continue refresh so the loop rule's
     `getLocalOuts` does not see a second declaration of the pattern variable;
   - the initial `boolean boolv = guard;` keeps the original guard, whose pattern
     assignment rules are already supported;
   - guard = reference to `boolv`;
   - position and comments from the original loop.
8. Copy the loop specification and loop contracts from the original loop to the new
   `while`.
9. Emit `whenFalse` declarations after the loop iff `whenFalse` is non-empty and the
   original body contains no unlabeled `break` at loop depth 0.
10. Splice the rewritten statements back into the list and return it. The after-loop
    declarations stay in the same block list, so they are visible to the statements
    that follow the loop.

The transformer must not share mutable state between applications.

### Break and continue analysis

- After-loop variables are suppressed if
  `OuterBreakContinueAndReturnCollector(originalBody, List.of(), services)` reports a
  `break` with no label. Breaks in nested loops/switches are not collected; labeled
  breaks do not target an unlabeled loop.
- Continue rewriting uses loop depth, not loop-and-switch depth: an unlabeled
  `continue` inside a `switch` still targets the surrounding loop.
- Labeled loops are out of scope for this rule; their continues are left untouched.

### Priority

Add a `pattern_loop_binding` rule-set entry and a cost below every loop treatment, so
the rewrite fires before loop-scope invariant/expand and before the normalizers
consume the loop. Because the rewritten guard is a plain variable, the rule fires
exactly once per loop and then no longer matches.

## JML visibility

`JMLSpecFactory.collectLocalVariablesVisibleTo` currently knows only `If`. Extend it
with the same flow rules as the proof rewrite:

- `while` body: add `whenTrue(guard)`.
- `for` body: add the existing for-init variables plus `whenTrue(guard)`.
- `do` body: no additional pattern variables.
- After a `while` / `for` / `do` in the same block: add `whenFalse(guard)` iff the
  body has no unlabeled break.
- Labeled loops: body visibility works; after-loop visibility stays conservative and
  is not exposed.
- A `LabeledStatement` wrapper is traversed for body visibility, but does not itself
  introduce after-loop variables.

The JML predicate and the proof transformer must use the same break analysis, so a
JML assertion that is accepted at load time can actually be proved.

## Testing

### Transformer unit tests

- Simple `while` with `x instanceof String s`: declaration, loop body, after-loop
  list is empty.
- Negated `while` with `!(x instanceof String s)`: after-loop declaration present.
- Break in the body: after-loop declaration absent.
- Continue at loop depth 0: rewritten to `{ b = e; continue; }`.
- Continue in a nested loop: left untouched.
- `for` with body and update use: update inside the bound body, init scoping block,
  after-loop declaration outside the block.
- `do`: first body unbound, generated `while` bound, after-loop declaration outside.
- Loop specification / contract copying: the new `while` is found by the
  specification repository.

### Rule tests

In the style of `TestPatternIfRules`:

- `patternLoopUnfold` applies to a binding loop in the program block.
- It does not apply to a non-binding loop.
- It applies exactly once; the rewritten loop is not matched again.
- A labeled loop and an unbraced loop body are not rewritten.
- The generated program has the expected shape and declaration placement.
- A loop inside a nested block is covered by the end-to-end proof; the nested rule
  becomes applicable once the enclosing block is part of the active program.

### End-to-end proofs

- `while` body: the proof closes with a JML assertion that uses `s`.
- `while` after: `while (!(o instanceof String s)) { ... }` followed by `s.length()`
  closes.
- `for` body and update: both use `s`.
- `do` after: the variable is available after the loop, not in the body.
- A loop with a `break` does not expose the variable after the loop; the
  reference is rejected by the Java parser.
- Loop-invariant treatment: a `while` with a `loop_invariant` and a bound body.
- All four loop options: loop-scope invariant, loop-scope expand, loop invariant,
  loop expand. Use a project-file fixture if the default environment does not enable
  the loop rule sets.

## Risks and limitations

- `whenFalse` is conservative for `&&`; after-loop bindings are not inferred there.
- `#posBinding` re-evaluates the `instanceof` operand. This is the same limitation as
  the existing `if` implementation; loops inherit it.
- A `for` guard that uses a for-init variable inside the matched expression cannot be
  recomputed outside the init block. The transformer must skip the after-loop binding
  for that case conservatively.
- The rewrite adds an auxiliary boolean variable. Loop-invariant rules include it in
  their local-variable bookkeeping; invariants do not mention it, so this is expected
  to be harmless but should be covered by the invariant tests.
- Labeled loops, unbraced loop bodies, and switch-block edge cases are conservatively
  excluded. They keep the current behavior: body bindings through the generated
  `if`, no after-loop bindings.
- A user who manually applies a loop rule before `patternLoopUnfold` loses the
  after-loop declarations. Automatic proof search always tries the rewrite first.
